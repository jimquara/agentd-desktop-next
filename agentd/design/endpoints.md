# Endpoint kinds per agent, and how agentd writes them

Research for libraos/agentd-desktop-next#12 (part of libraos/agentd-core#898). It covers first-run screen 2: use an API key or a gateway instead of the person's own account, per agent, offering only the choices that agent accepts.

Sources were read on 2026-11-18:

- **AC** is `libraos/agentd-core` at `0f721660`. Paths are relative to `internal/agentd/` unless they start with `docs/`.
- **Wiki** is `libraos/wiki` at `64ec5b7`, `product/agentd-connections.md`.
- Vendor documentation is cited by URL.
- Locally installed clients: Claude Code 2.1.327 and Codex 0.169.0. Some Codex facts come from strings in the 0.169.0 binary; those are marked "binary". opencode is not installed here, so its column rests on its documentation only.

No credential file was opened or printed.

## 1. What each agent accepts

Wire formats:

- **Messages** is the Anthropic Messages API (`/v1/messages`).
- **Chat** is OpenAI Chat Completions (`/v1/chat/completions`).
- **Responses** is the OpenAI Responses API (`/v1/responses`).

Each agent's own configuration lives in these files:

- **Claude Code:** `~/.claude/settings.json`, whose `env` block takes every variable below, or the shell environment. Source: https://code.claude.com/docs/en/settings.
- **Codex:** `~/.codex/config.toml`. Codex ignores `model_provider` and `model_providers` in a project's `.codex/config.toml`. Source: https://learn.chatgpt.com/docs/config-file/config-reference.
- **opencode:** `~/.config/opencode/opencode.json(c)`. Source: https://opencode.ai/docs/config/.

So screen 2 offers each agent only these choices:

- **Claude Code:** Gateway, Anthropic key, Bedrock, Ollama, and a custom endpoint that serves Messages. No OpenAI key.
- **Codex:** Gateway, OpenAI key, Bedrock, Ollama, and a custom endpoint that serves Responses. No Anthropic key.
- **opencode:** all six. A custom endpoint needs its wire format chosen.

One configuration-schema risk for opencode:

- agentd's opencode workers write the old keys: `provider` / `npm` / `options` (AC `opencodeworker.go:239-244`).
- opencode's current documentation shows only the new keys: `providers` / `package` / `settings`. It does not say whether the old keys are still read (https://opencode.ai/docs/providers/, https://opencode.ai/docs/config/).
- This was not verified, because opencode is not installed here.
- Anything written into opencode's own file has to follow whichever schema the installed opencode reads.

## 2. What agentd writes today

### Commands that exist

None of agentd's model-access commands writes an agent's own configuration. `agentd connect [claude|codex|opencode]` writes only these into each agent's own files: the agentd MCP server, Claude Code hooks, Codex `default_tools_approval_mode`, opencode `mcp.agentd`, and Skills. It writes no endpoint (AC `dispatch.go:1663`). Model access lives in three other places:

- **Local dispatched workers.** These settings live in agentd's own `config.toml`: `[gateway]` (`url`, `key_file`), and `[dispatch]` (`claude_base_url`/`claude_key_file`, `codex_base_url`/`codex_key_file`, `opencode_base_url`/`opencode_key_file`/`opencode_model`) (AC `config.go:384-447`, `docs/configuration.md:47-51,101-103`).
  - agentd turns them into per-worker settings at launch:
    - Claude: an `env` block with `ANTHROPIC_BASE_URL`, plus an `apiKeyHelper`, in the worker's own settings file (AC `workerresult.go:1006-1014`).
    - Codex: `-c model_providers.agentd.*` with `wire_api = "responses"`, plus `--profile agentd` (AC `handoffdeps.go:2143-2156`).
    - opencode: `OPENCODE_CONFIG_CONTENT` with `OPENCODE_DISABLE_PROJECT_CONFIG=1` (AC `workertool_opencode.go:82-95`, `opencodeworker.go:219-247`).
  - With none of these set, Claude and Codex workers use the person's own login or provider. opencode refuses to start without a gateway (AC `opencodeworker.go:68-78`).
  - The only command that writes these keys is `agentd init --model-key FILE [--model-base URL]` (AC `onboard.go:1587-1588`). It writes `[gateway] url = BASE/v1`, `claude_base_url = BASE` and `codex_base_url = BASE/v1`, all with the same key file (AC `onboard.go:946-956`).
    - It writes no `opencode_*`.
    - It refuses a config that already has `[gateway]` or `[dispatch]` (AC `onboard.go:1002-1012`).
  - `agentd config set` refuses all of these keys with "setting is not writable" (AC `settings_config.go:271-414`).
- **Cloud Workers.** `agentd handoff offer --cloud` takes `--model-access libraos|byok|subscription`, `--anthropic-key-file F` and `--openai-key-file F`. A BYOK job gets `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` with no base URL override; a libraos job gets `ANTHROPIC_BASE_URL`/`OPENAI_BASE_URL` set to the Gateway (AC `dispatch.go:334,1607`, `cloudcmd.go:29`, `cloudbyok.go:347-357`).
- **agentd server account pool.** `agentd account add NAME --kind api_key|gateway_key --provider anthropic|openai [--base-url URL] --key-file FILE` (AC `modelaccounts.go:174`). Only Claude Code (Anthropic) and Codex (OpenAI) can use it (AC `docs/model-accounts.md:60-63`).

The wiki says only that "Sessions and workers all need a model; they use the customer's own Claude Code or Codex account, or Gateway. AgentD does not include model access" (Wiki, "Two optional services not drawn"). It names no command.

### Gaps to file against agentd-core (listed here, not filed)

1. **No command writes a model endpoint into an agent's own configuration** for any of the 18 cells: Claude Code `settings.json` `env` / `apiKeyHelper`, Codex `config.toml` `model_provider(s)`, opencode `opencode.json` `provider(s)`. `agentd connect` stops at MCP, hooks and Skills.
2. **No way out.** No command removes such an endpoint and returns the agent to the person's own login. Screen 2 needs both ways.
3. **`[dispatch]` and `[gateway]` endpoint keys are not settable after init.** `agentd config set` refuses `dispatch.{claude,codex,opencode}_{base_url,key_file}` and `gateway.{url,key_file}`, and `init --model-key` refuses once either table exists. Changing endpoint means hand-editing `config.toml`.
4. **`init --model-key` leaves opencode out**: it writes no `opencode_model`, so opencode workers stay refused under the Gateway.
5. **No direct API key for local workers.** `claude_key_file` requires `claude_base_url`, and there is no `--anthropic-key-file` / `--openai-key-file` outside `--cloud`.
6. **No Bedrock** anywhere in agentd: local `[dispatch]`, Cloud `--model-access`, or `account add --provider`.
7. **No keyless local endpoint.** Ollama needs no key, but `codex_base_url` requires `codex_key_file` and `init` requires `--model-key`.
8. **Custom endpoint has no wire-format choice.** `--model-base` assumes one Messages origin plus a Responses `/v1`. Nothing records which formats an endpoint serves, so agentd cannot offer each agent only what that endpoint can carry.
9. **opencode configuration schema.** Check whether current opencode still reads the old `provider`/`npm`/`options` keys agentd writes into `OPENCODE_CONFIG_CONTENT`, or only the documented new `providers`/`package`/`settings` ones.

## 3. How the app applies a choice without holding the key

The two options:

- **(A) agentd writes the agent's own config.** The app calls agentd, and agentd writes a reference to a key file, never the key itself:
  - Claude: `apiKeyHelper` or `env`.
  - Codex: `env_key`, or an `auth` command.
  - opencode: `{file:…}`.
- **(B) The app adds a second provider instance, "Gateway".** It is a `ProviderInstanceConfig` whose `environment` holds `ANTHROPIC_BASE_URL` and similar variables, with secret references (`packages/contracts/src/providerInstance.ts:25-82`, edited in `ProviderEnvironmentSection`, `apps/web/src/components/settings/ProviderInstanceCard.tsx:356`).

Trade-off in three lines:

- (A) is one truth for every surface: terminal sessions, agentd's workers (Claude and Codex inherit the person's own config) and the app all use the same endpoint, and all three agents can be configured this way. But it needs new agentd-core commands (gaps 1-2), and it changes the person's agent setup outside the app too.
- (B) needs no agentd change, is reversible per instance, and keeps the person's own login as the default instance. But only sessions the app starts see it, agentd's workers and terminal sessions do not, and environment variables alone cannot set a Codex provider (Codex needs `config.toml` or `-c` arguments), so it does not hold for all three agents.
- (B) also puts the key, or a secret provider for it, in the app, against "the app includes no model access" and "agentd is the authority".

**Recommendation: (A).** agentd writes the agent's own configuration, and the app only calls agentd and shows the result.

- Screen 2 needs gaps 1, 2 and 8 closed: a write command, a remove command, and an endpoint's formats recorded so agentd can offer each agent only what it accepts.
- opencode workers do not use the person's own provider. agentd's `OPENCODE_CONFIG_CONTENT` is read after every config file and wins, and its `enabled_providers` names only agentd's provider (AC `opencodeworker.go:24-26,229`). So for opencode, the same command must also set agentd's `[dispatch] opencode_*` keys (gap 4).
- Until those commands exist, screen 2 can offer only "LibraOS Gateway for agentd's workers" through `agentd init --model-key`, and only on a config without `[gateway]` or `[dispatch]`.
